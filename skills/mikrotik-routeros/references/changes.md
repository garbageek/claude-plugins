# Changes, Backups and Recovery

## Prepare and verify

Before a change, record the exact rows, previous values and dependent services. RouterOS row numbers can change across prints and sessions. Match by stable properties, check the number of matches, and distinguish dynamic rows from editable configuration. Re-read before retrying a failed batch because earlier commands may have applied.

For a write that may break remote management, confirm a working recovery path before applying: a verified Safe Mode session for a supported small change, a verified timed inverse appropriate to that change, or an independently reachable local management path. A second login over the same link and a backup that cannot be restored after lockout do not meet this requirement. If protection is unavailable or loses ownership, stop affected writes and report the exact missing prerequisite. Never use Safe Mode as a substitute for console/recovery access on an operation that requires reboot.

After each batch, re-read the changed rows and verify the affected workflow from the relevant client or network. Keep the original management session open and verify a fresh login. Two sessions over the same bridge share the same failure path. Stop dependent changes on a failed check, then verify the outcome of any rollback. Record durable live changes in the relevant service or topology note.

Keep a compact before/after diff of meaningful fields, expected effect and the verification point. A successful tool response records an attempted action. Classify a correct re-read as configured, and reserve verified working for the relevant functional check. If the check requires a client or external vantage point that is unavailable, record that as unverified.

## Multi-router sequence

Resolve every target and note which device carries management for another. Capture per-device baseline and plan dependent actions in order. Apply one recoverable increment at a time. Check the changed device and the downstream management and service paths before advancing. Track Safe Mode ownership, commit or rollback, and functional evidence separately per device. A failure on a later router leaves earlier commits in place. Recover only the affected scope. After loss of access, keep the affected device's state unknown until a fresh read shows what persisted or reverted.

## DHCP reservation

Resolve the DHCP owner for the client's VLAN and inspect the server, network, pool and leases. Match the client MAC and any applicable client ID to the current reservation or dynamic lease and check whether anyone already holds the requested IP. Verify scope and address ownership before making the intended lease static or adding a new reservation. If the correct reservation exists, report it without writing. Re-read the unique reservation and verify the next client lease/renewal when reachable. Report an unobserved renewal separately. [DHCP server](https://manual.mikrotik.com/docs/network-management/dhcp/server/).

## Changes that can interrupt access

- **Bridge and VLAN:** Trace ingress, every trunk and access port, and the bridge/CPU port for management. Stage tagged/untagged membership, PVID and frame admission before enabling filtering. Inspect `current-tagged` and `current-untagged` as well as configured members. PVIDs can add dynamic untagged entries, including for the bridge itself. Some releases also add dynamic CPU membership. Check switch-chip support and the actual hardware-offload flag. Verify management, DHCP and intended forwarding from relevant ports after the change. [Bridge VLAN filtering](https://manual.mikrotik.com/docs/bridging-and-switching/) and [switch-chip configurations](https://manual.mikrotik.com/docs/bridging-and-switching/user-guides/basic-vlan-switching/).
- **Firewall, NAT and policy routing:** Trace ingress, chain, rule order, interface lists and the selected routing table. Stage access before removing its prior path. Use a new connection from the affected source to verify NAT or policy changes because existing sessions can retain connection state. Check FastTrack eligibility when a flow must use a non-main route or a queue. Avoid a global connection-table flush. [Packet flow](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/packet-flow-in-routeros/) and [connection tracking](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/connection-tracking/).
- **Wireless backhaul:** Check both endpoints, the station scan list, country/channel settings, supported widths and driver families. Legacy `wireless` and newer `wifi` cannot interoperate in station-bridge mode. Treat a driver swap as a migration of the link and prepare recovery independent of that radio. [Wireless Interface](https://manual.mikrotik.com/docs/wireless/abgn/wireless-interface/) and [Wi-Fi](https://manual.mikrotik.com/docs/wireless/wifi/).
- **WAN failover:** Distinguish a reachable ISP next hop from a working Internet path. For recursive failover, pin each probe destination to its intended uplink and verify the immediate gateway, table, scope and target scope. Check NAT on the backup WAN and verify client routes, DNS and new connections during failover and failback. Routes on the primary router address uplink failure while it is alive. A separate gateway handover is needed for router failure. [WAN backup](https://manual.mikrotik.com/docs/high-availability-solutions/load-balancing/failover-wan-backup/).
- **Standby gateway handover:** For a design with one DHCP owner, confirm the primary cannot serve the segment before enabling standby DHCP or taking over its address. A failed ping does not prove either condition. Check pool overlap, reservations, and DNS answers for local names. Prove backup uplink and DNS from an authorized client without adding a second DHCP server to the production segment. On restoration, release any shared address and stop standby DHCP before returning primary DHCP to the segment. Verify which server issued the renewed lease, client gateway and DNS, and actual application reachability. [DHCP Server](https://manual.mikrotik.com/docs/network-management/dhcp/server/).

For authorized SSH key enrollment, confirm the account, trusted host fingerprint and supported public-key format. Generate the pair on the management host; upload only the public key for inbound access and import it under `/user ssh-keys`. Inspect the current password-authentication setting first: adding a key can disable password login for that account under `yes-if-no-key`. Keep the existing session open and verify a fresh key-only login before restricting access or removing an old key. Remove only the temporary public-key upload after verification.

For authorized WAN health automation, first observe a probe without recovery actions. Verify egress through the intended uplink, threshold behavior and initial `unknown` transitions. Check the permissions of the actual Netwatch execution context. Before adding actions that disrupt service, corroborate a failure across endpoints and limit how often recovery runs. [Netwatch](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/netwatch/).

## Safe Mode

Open an interactive session with `ssh -tt <alias>` (without a remote command) or use WinBox. Enter CLI Safe Mode with Ctrl+X or F4 and confirm `<SAFE>`. Leave any existing owner's session alone. Changes take effect immediately. RouterOS records floating undo entries in `/system/history`, including changes from other login sessions while the guard is active.

- For persistent MCP Safe Mode, check the catalog and the provider's session semantics first. Keep the device title and backend instance fixed, then verify state on the router. [MCP session limits](integration.md#wiresage-capabilities).
- Commit with Ctrl+X after verification. Use Ctrl+D to undo and exit. Reserve `/quit` for after commit. For an abnormal disconnect the manual cites a TCP timeout of about nine minutes for Telnet or WinBox. Confirm the device's state after reconnecting.
- Keep batches well below the approximately 100-action history capacity; overflow can end protection. Do not run imports or scripts with unbounded changes. Safe Mode is not protection for reset, backup restore, or upgrades requiring a reboot.
- A supervised PTY can keep ownership across command batches and independent checks. Keep the PTY open while validating. Each separate SSH exec command has its own session.
- RouterOS 7.18 release notes announce scriptable Safe Mode and a handler. On builds that expose it, inspect `/safe-mode/print` or `:put [/safe-mode/get]` and discover supported commands with target help. For a verified scriptable workflow, take ownership, confirm `current=true` in that same execution context, apply, verify and release on success or unroll on failure. A separate read session may report `enabled=true` with `current=false`. Check clean exit, script error and disconnect behavior on the same version and transport before adopting it for production. Use the interactive workflow when those semantics are unknown. [RouterOS 7.18 release notes](https://forum.mikrotik.com/t/v7-18-2-stable-is-released/182200).

See [Configuration Management](https://manual.mikrotik.com/docs/getting-started/configuration-management/) and [Console](https://manual.mikrotik.com/docs/management-tools/console/).

## Timed recovery

A rollback timer runs the exact inverse of the planned change. RouterOS retains saved configuration on reboot. Use a scheduled reboot only for a recovery scenario that reboot actually addresses.

1. Capture the original state and prepare narrowly scoped inverse commands that tolerate partial application. Check scheduler availability, owner and policy against the commands actually invoked. Account for any difference between scheduler and script permissions. Keep the scheduled action available until it succeeds or is deliberately disarmed.
2. On a synchronized router, set a unique entry with explicit future `start-date` and `start-time`, `interval=0s` and no weekday schedule where supported. Verify the exact deadline and `run-count=0` with `/system scheduler print detail` before applying. Allow for local timezone, midnight and validation time. An interval by itself is unsuitable for a one-shot deadline. For clock/NTP changes that may move the clock, use a recovery path independent of router wall time.
3. If using the timer alone, remove or disable the exact entry after successful verification and confirm it is disarmed. If time runs short, abort the change while there is still time to restore and verify the original state.
4. When combining with Safe Mode, arm the timer before taking Safe Mode and disarm it after leaving Safe Mode, with time to spare. Cancellation inside Safe Mode can be undone by a subsequent rollback. Also account for the timer's inverse commands entering Safe Mode history if they run while it is active. Use both only when that execution ordering has been checked. After rollback or timeout, verify the exact prior values and client access. A scheduler run counter alone only indicates that it ran.

[Scheduler](https://manual.mikrotik.com/docs/system-information-and-utilities/scheduler/) and [scripting permissions](https://manual.mikrotik.com/docs/developer-guides/scripting/).

## Backup and restore

- For review use text `/export` (or a scoped export). Select `compact` for non-default settings, `terse` for commands with full menu paths, and `verbose` when defaults matter. Verify syntax on the target version. An export with `file=` writes on the router. Check output for omitted menus and `#error exporting`; an SSH success code does not prove completeness.
- When an authorized operation needs a recovery copy, pair a text export with an encrypted binary backup as appropriate. Supply a backup password via a protected workflow and verify encryption settings. `dont-encrypt=no` alone does not encrypt a backup without a password. Use binary restore on the same device and RouterOS version where possible. Review text for migration. User passwords, installed certificates and SSH keys need separate recovery arrangements.
- Request sensitive export only when needed and authorized. Even an ordinary export can contain secrets embedded in script source or comments. Transfer via an authenticated channel, keep local directories 0700/files 0600, verify size and checksums (exclude the checksum manifest itself), and remove only exact temporary router files after verifying the local copy. No secret material in Git, chat, or external tools.
- Import executes commands; it is not a transactional restore. Check package/port differences, exact target version and supported `verbose=yes dry-run` syntax. A dry run checks parsing and does not prove access after apply. Do not silently fall back to a real import when dry run is unsupported. Never use a `.auto.rsc` filename for staging; upload can trigger execution.
- Before an upgrade check architecture, package set, free flash, release notes, power, device mode and recovery access. Stage one router at a time when it carries management for others. Verify the booted RouterOS and packages, radios, routes, DHCP and a fresh login before proceeding. Compare RouterBOOT `current-firmware` and `upgrade-firmware` independently.
- For lost access try a tested local console or MAC WinBox on a known reachable, allowed L2 segment. MAC WinBox still depends on the L2 path and its interface list. Reserve restore, reset and Netinstall for recovery work with verified backups and the required physical access. [MAC server](https://manual.mikrotik.com/docs/management-tools/mac-server/).
- Before physical recovery, match the exact `model` from `/system routerboard print` to its product guide and inspect `/system routerboard settings print` while reachable. Reset button behavior depends on the model, the LED stage and Protected RouterBOOT. Follow the product's recovery procedure and confirm whether the action resets configuration or erases storage. [RouterBOARD settings](https://manual.mikrotik.com/docs/cli-reference/system/routerboard/settings/).
