# Read-Only Diagnostics

Use the configured SSH alias and pinned host key. On Linux, bound reads with `timeout 15s ssh -o BatchMode=yes -o StrictHostKeyChecking=yes -o ConnectTimeout=5 <alias> '/system identity print; /system resource print'`. Give longer, bounded probes their own budget. Send optional commands separately so an unsupported menu cannot abort the rest of the audit. Inspect command output for RouterOS errors and check that all requested reads completed.

## Inventory and path

| Question | Reads to select from |
| --- | --- |
| Correct device, clock, resources? | `/system identity print`, `/system resource print`, `/system package print`, `/system routerboard print`, `/system clock print`, `/system ntp client print`. Health sensors are model-dependent. |
| Where does a client enter? | Correlate `/ip arp print`, `/ip dhcp-server lease print` and `/interface bridge host print` filtered to its IP/MAC. Walk bridge ports and wireless peers; neighbor discovery does not prove a physical cable. |
| Is the path forwarding? | `/interface bridge port print detail`, `/interface bridge monitor <bridge> once`, `/interface bridge vlan print`, `/interface list member print`. Inspect actual hardware-offload and VLAN membership, not just configured flags. |
| Which path reaches the Internet? | `/ip address print`, `/ip dhcp-client print detail`, `/ip route print detail where active`, RouterOS v7 `/routing rule print`; inspect routing marks, VRF and IPv6 when relevant. |
| Do firewall, NAT or queues explain the symptom? | Read relevant filter/NAT/mangle rules in order plus `print stats`, interface lists, and simple/queue-tree counters. Check the real ingress, egress and chain. Don't clear counters or conntrack. |
| What changed? | Filter `/log print without-paging where ...` by relevant topics/messages. Compare device clocks and uptime before correlating timestamps. Inspect selected scheduler fields, avoiding script bodies with credentials. |

Use `/interface ethernet monitor <port> once`, `/interface ethernet print stats`, `/interface monitor-traffic <iface> once` and `/interface print stats-detail` as supported. Compare negotiated rate/duplex, link-down time, FCS errors and queue drops. Take two snapshots over a known interval to measure growth. Avoid unbounded `follow`, `monitor`, and `/ip route check` over batch SSH.

On fiber, check link flaps, `sfp-rx-loss`, FCS deltas and optical RX/TX when the module exposes DDM. Compare optical power against that module's specifications. A bad EEPROM checksum can suppress DDM, so unavailable optical readings leave the optical budget unverified. Correlate with active route, WAN lease and ISP next-hop probes. [Ethernet and SFP](https://manual.mikrotik.com/docs/wired-connections/ethernet/).

## Triage by symptom

| Symptom | Useful next check |
| --- | --- |
| One client lacks Internet | Trace its DHCP lease/gateway, ARP and bridge/VLAN attachment, then check gateway reachability, a public IP and DNS from that client. If peers work, inspect its specific forward/NAT path. Verify the failing client can reach the actual service. |
| All clients lack Internet | Check active WAN status, default route and ISP/public IP/DNS reachability from the gateway. If the router works, trace a client forward/NAT flow and recent changes. Router probes exercise output. Verify service from affected clients after recovery. |
| Device missing from neighbors | Check discovery settings, forwarding membership, learned MAC, ARP and leases. Confirm with a management read or leave reachability/attachment unknown. [Discovery](discovery.md). |
| Forwarded port or return traffic fails | Identify the actual ingress and service owner, then trace the new flow and reply in [packet paths](packet-paths.md). |
| A VLAN client cannot reach the gateway | Walk VLAN membership and management access using [VLAN checks](packet-paths.md#vlan-cannot-reach-the-gateway). |
| Small packets succeed, HTTPS or large transfers stall | Compare IPv4 pings to a known ICMP responder using small and near-MTU packets with `do-not-fragment count=3`, from the affected path. RouterOS `size=` includes IP/ICMP headers and differs from Linux payload size. Check tunnel overhead and ICMP fragmentation-needed or IPv6 Packet Too Big delivery before changing MTU or clamping TCP MSS. [Ping](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/ping/) |
| Traffic passes but firewall or queue counters are flat | Inspect `/interface ethernet switch print` on supported hardware and map ingress and egress to chips. Check the active bridge port `H` flag, FastTrack connections, and L3HW only if that hardware supports it. A route's `H` flag indicates eligibility. Check actual L3HW state before concluding that packets were routed in hardware. [Switch chips](https://manual.mikrotik.com/docs/bridging-and-switching/switch-chip-features/) · [L3HW](https://manual.mikrotik.com/docs/bridging-and-switching/l3-hardware-offloading/) |
| WireGuard peers have no recent handshake | Verify endpoint resolution and routing, listener port, and UDP reachability via the expected uplink. Check the router's input rules and any upstream NAT. Use selected peer fields such as `last-handshake`, `rx` and `tx` and keep keys out of output. |
| WireGuard handshakes work, but remote services fail | Check tunnel IPs, both directions of `allowed-address`, actual route and return route, and forward/NAT rules. Verify traffic to an allowed tunnel IP and the expected service, then MTU if only large transfers fail. [WireGuard](https://manual.mikrotik.com/docs/virtual-private-networks/wireguard/) |
| Unexpected reboots or unexplained CPU load | Record uptime, reboot logs and resource counters. Inspect supported health sensors and `/system watchdog print`. Use a bounded CPU profile when necessary. Preserve any existing crash artifacts before a subsequent reboot. [Watchdog](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/watchdog) |
| Intermittent loss or low throughput | Correlate symptom times across routers. Compare link-down times, CRC and queue-drop deltas, CPU and free storage, lease changes and evidence of competing DHCP offers. Compare results over the actual path. A quiet sample only establishes that window. |
| Router works, end-to-end flow fails | Follow the forward and return paths across routers from the affected source. Confirm each next hop or service and mark the first missing observation. Verify at the destination to close the incident. |
| Access dropped after a change | Distinguish loss of the management path from router or service failure using a still-open or independently available path. Check Safe Mode ownership and verify original or intended values on reconnect. [Recovery](changes.md#safe-mode). |

During traceroute, loss confined to an intermediate hop can be a slow or rate-limited ICMP reply. Compare subsequent hops and the final destination before identifying a failing segment.

## Slow Internet and large traffic consumers

1. Follow the client path. Compare short ping series across each suspected hop and from the edge to the ISP next hop and public endpoints. Record origin, count, loss and latency range. Measure during the reported symptom where possible. Idle ping establishes reachability and baseline latency.
2. Sample WAN byte and queue-drop counters during normal traffic. Calculate rate as eight times the byte delta divided by elapsed seconds. WAN RX is download and TX is upload. Compare contemporaneous LAN and backhaul rates to detect local transfers.
3. For IPv4 NAT traffic, sample `/ip firewall connection print as-value` filtered to the relevant NAT connections. Use `orig-bytes` and `repl-bytes` for deltas. Keep FastTrack subcounters separate. For outbound src-NAT group by internal original source. For inbound dst-NAT identify the translated internal endpoint and reverse the upload/download mapping. Match protocol and endpoint tuples with entry identity where available. Exclude pre-existing totals, counter resets and ambiguous reused IDs. A newly observed row has an unknown lifetime unless its creation falls inside the sample.
4. Check routed IPv6 separately. Reconcile approximate per-host rates with WAN deltas before filtering the report. Short-lived flows, hardware offload and router traffic may leave a gap. Map hosts using current leases/ARP. Include traffic from the named client when measuring that client or ranking all clients. Exclude that client's traffic from the reported ranking only when asked to report on other clients. Report the observation window and coverage. Multi-day attribution requires pre-existing per-host telemetry. [Connection counters](https://manual.mikrotik.com/docs/cli-reference/ip/firewall/connection/).

Torch and sniffers can disable FastPath/FastTrack during capture. CPU-only tools can miss hardware-offloaded traffic. Traffic Flow also misses offloaded traffic and FastTracked packets. Wireless scans can disconnect clients. Keep these and bandwidth tests outside a passive audit. [Packet flow](https://manual.mikrotik.com/docs/firewall-and-quality-of-service/packet-flow-in-routeros/) and [Traffic Flow](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/traffic-flow/).

For an authorized capture, scope the supported filters to the actual interface, endpoint, protocol and port. Use a finite duration and confirm it stopped, especially on timeout. Record how capture changes the forwarding path. Treat saved packet data as private. [Packet sniffer](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/packet-sniffer/).

## Wi-Fi, DNS and LTE

- **Wireless:** Check the installed driver. Use the relevant `/interface wireless registration-table print stats` or `/interface wifi registration-table print detail` and compare both endpoints. Record band, channel, width, RSSI/SNR, PHY rates, radio or client load, steering/roaming evidence, retries and queue-drop deltas when exposed. Compare Wi-Fi-to-local-peer, AP uplink, WAN and DNS observations to isolate the failing boundary. Correlate logs and check channel or radar/CAC events before attributing a disconnect to DFS. Verify from the affected client during a comparable symptom window. [Wireless Interface](https://manual.mikrotik.com/docs/wireless/abgn/wireless-interface/) and [Wi-Fi](https://manual.mikrotik.com/docs/wireless/wifi/).
- **DNS:** Compare WAN peer DNS, router upstreams/DoH/static records, DHCP network options, and the client's actual resolver. Query each advertised resolver directly for a local and public name. Record status, answer and delay. Check dead upstreams and loops independently. RouterOS can keep using a responsive upstream after fallback. With `use-doh-server` set, plain upstreams normally bootstrap the DoH hostname and do not provide automatic fallback for failed DoH queries. DHCP resolver selection is client-controlled. [DNS](https://manual.mikrotik.com/docs/network-management/dns/) and [DoH settings](https://manual.mikrotik.com/docs/cli-reference/ip/dns/).
- **LTE:** Use `/interface lte monitor <iface> once` and check registration, APN, assigned IP, active route, session uptime, signal and LTE counters. Select necessary fields to avoid exposing SIM, modem and location identifiers. Confirm probe egress by checking routing context and interface activity, especially with both uplinks up. Test public IP and DNS/application reachability separately. Verify forwarded traffic from a client using LTE before declaring it a usable fallback. [LTE/5G](https://manual.mikrotik.com/docs/mobile-networking/lte-5g/).
- **Clock:** Check date, timezone, NTP status and selected peer. Where the router serves time, query it from LAN and check the reply's sync state. If the date jumps, compare clock events with GPS validity and NTP peers. GPS `set-system-time=yes` permits clock updates. A matching stale date alone cannot establish the cause. Bound `/system ntp monitor-peers` externally because it can run continuously. [Clock](https://manual.mikrotik.com/docs/system-information-and-utilities/clock/) and [NTP peer monitoring](https://manual.mikrotik.com/docs/cli-reference/system/ntp/monitor-peers/).

For existing WAN health probes, use `/tool netwatch print stats` as supported. Inspect the status, time of last transition, failed-test deltas and thresholds. Check probe routing before interpreting a healthy result as evidence for a particular uplink. [Netwatch](https://manual.mikrotik.com/docs/diagnostics-monitoring-and-troubleshooting/netwatch/).

For a sustained fault or crash requiring vendor support, use `/system sup-output` when authorized. It writes a file and requires adequate storage. Use a unique filename to preserve existing evidence. Collect it while the fault is present or before rebooting again. Treat `supout.rif` and existing `autosupout*.rif` as private configuration and log artifacts. Transfer them to protected local storage and only send them externally with authorization. [Support output](https://manual.mikrotik.com/docs/getting-started/supout-rif).
