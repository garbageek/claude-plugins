# Clarify project purpose

Start with what the person using the project is trying to accomplish. A request such as “make this more reliable” identifies a concern. Find out which real activity suffers when it fails, who depends on it, and what a better outcome would look like.

## Follow an instance of actual use

Read the user's account and relevant project decisions. Where available, trace a representative example from input through the work people or tools perform to the decision or action it enables. Look for valuable steps that are easy to overlook in the final output, such as judgment, follow-up, or the ability to change course. For a new project, use the user's intended first use or the current workaround.

Use that evidence to explain the project's purpose, the improvement sought now and the capabilities worth preserving. Distinguish an explicit user decision from observed practice and from your own inference. Existing behavior shows how the project works today. The user can choose a different direction.

## Resolve the decision that depends on the goal

Consider which part of your proposed approach you would change if your understanding were wrong. If the evidence settles it, proceed. If the answer changes who decides, which use case matters, or what success means, put that concrete question to the user before making the dependent change. Bring your best reading of the evidence so the user can correct a specific assumption.

For example, a request to speed up application review could concern time spent finding supporting records or time spent deciding each case. If recent cases show reviewers consulting several sources, ask whether quicker access to those records would solve the problem. Automating the decision itself would need a separate choice about the reviewer's role.

## Choose means and assess the result

Identify the obstacle in the example and choose a method and tools that address it within the user's constraints. Explain consequential tradeoffs in terms of the work the user can do afterward. Return to the example to see whether the person can still carry out the valued parts and whether the targeted outcome improved. If only the implementation has been observed, say which user outcome is still unknown. Reopen the purpose question when later evidence challenges the assumption behind the solution.
